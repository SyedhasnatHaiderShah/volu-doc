# 05 · Observability

**Status:** 🟢 Approved

How we know what's happening in production. The four pillars: logs, metrics, traces, errors — plus alerting and dashboards.

---

## Stack

- **Logs:** Pino (app) → CloudWatch Logs → forwarded to Grafana Loki for query.
- **Metrics:** Prometheus client libs in app → scraped by Grafana Agent → Grafana Mimir.
- **Traces:** OpenTelemetry SDK in app → OTLP exporter → Grafana Tempo.
- **Errors:** Sentry (cloud-hosted).
- **Dashboards & Alerting:** Grafana.
- **Synthetic monitoring:** Better Stack (or AWS Synthetics).
- **Status page:** Statuspage.io or self-hosted.

---

## Correlation IDs

Every request gets a `traceId` (W3C `traceparent`) at ALB or generated by API Gateway. Propagated through:
- Backend: NestJS request context middleware adds `traceId` to logs and outgoing HTTP/queue headers.
- Workers: Inherit `traceId` from job payload.
- Mobile: Sends `X-Request-Id` header; backend logs both client-supplied and server traceparent.

This means: a user reports an issue, we have their `traceId`, and we can trace the entire request through all systems.

## Logs

### Format

Structured JSON, one event per line:

```json
{
  "level": "info",
  "ts": "2026-04-23T14:30:00.123+04:00",
  "msg": "coupon.redeemed",
  "service": "volu-core",
  "traceId": "01HXX...",
  "spanId": "...",
  "userId": "01HX...",
  "merchantId": "01HX...",
  "couponId": "01HX...",
  "branchId": "01HX...",
  "durationMs": 124
}
```

### Levels

- `error` — unexpected failures; surfaced to Sentry.
- `warn` — anomalies; investigate but not page.
- `info` — significant business events (purchase, redemption, payout, login).
- `debug` — only enabled in staging for diagnosis.

### PII redaction

Pino redaction filter scrubs:
- Phone numbers (last 4 only kept)
- Email (domain only kept)
- Card-related fields (any reference to PAN-shaped strings)
- JWT tokens
- OTP codes
- KYC document content

### Retention

- Hot (queryable): 30 days in CloudWatch + Loki.
- Cold (audit): archived to S3 Glacier for 12 months.

## Traces

OpenTelemetry instrumentation auto-instruments:
- Incoming HTTP (NestJS)
- Outgoing HTTP (Dio in mobile, undici in backend)
- Database queries (Prisma)
- Redis operations
- BullMQ jobs

10% sample in production; 100% in staging.

A single trace shows: incoming request → controller → service → DB → external API → response. Total latency broken down per span.

## Errors (Sentry)

- Mobile, backend, admin all configured.
- Releases tagged with version + commit SHA so we can correlate errors with deploys.
- Source maps uploaded for admin & mobile.
- Errors grouped by stack hash; assignee + priority assigned per group.
- SLA: triage within 24h.

## Dashboards

Grafana dashboards organised by audience:

### Engineering dashboards
- **Service health (per service):** request rate, latency P50/P95/P99, error rate, in-flight requests.
- **Database:** CPU, connections, replication lag, slow queries, cache hit ratio.
- **Redis:** ops/sec, memory used, hit ratio, evictions.
- **Workers:** queue depth, processing rate, failure rate.
- **External APIs:** Stripe / Tabby / etc. latency + error rate.

### Product dashboards
- **Funnel:** install → reg → first view → first purchase → first redemption → repeat.
- **GMV & Revenue:** today, MTD, YoY.
- **Active deals & merchants:** trends.
- **Conversion rates:** view → cart → checkout → paid.

### Operations dashboards
- **KYC queue depth & age**
- **Deal moderation queue depth & age**
- **Payout queue & age**
- **Refund rate by merchant**
- **Support ticket SLA**

### Finance dashboards
- **Daily Stripe vs internal ledger diff**
- **Pending vs available vs paid-out balances**
- **Breakage revenue trend**
- **VAT collected / payable**

## Alerting

### Severity → channel

- **SEV-1 / SEV-2:** PagerDuty page (on-call ack required).
- **SEV-3:** Slack #ops-alerts (no page).
- **SEV-4:** Slack #ops-info (informational).

### Alert rules (sample)

| Metric | Condition | Severity |
|---|---|---|
| `http_request_error_rate` | > 1% for 5 min | SEV-2 |
| `http_request_error_rate` | > 5% for 2 min | SEV-1 |
| `http_request_p95_latency` | > 1000ms for 5 min | SEV-2 |
| `db_replication_lag_seconds` | > 30 for 5 min | SEV-2 |
| `db_connections` | > 90% pool size for 5 min | SEV-2 |
| `payment_failure_rate` | > 5% for 5 min | SEV-1 |
| `redemption_validate_p95_latency` | > 1500ms for 5 min | SEV-2 |
| `queue_depth` | > 1000 for 5 min | SEV-3 |
| `outbox_backlog_seconds` | > 300 for 2 min | SEV-2 |
| `crash_rate` (mobile) | > 0.5% | SEV-2 |
| `kms_decrypt_anomaly` | unusual pattern | SEV-2 |
| `failed_admin_logins` | > 20/min | SEV-2 |

### Alert fatigue prevention

- Every alert has a runbook link in [10-operations/02-runbooks.md](../10-operations/02-runbooks.md).
- Alerts review monthly: any "always firing" or "always ignored" alerts are tuned or removed.

## Synthetic monitoring

Better Stack runs from multiple geographies (UAE, EU, US) every 1 minute:

- `GET /health` returns 200
- `GET /api/v1/deals?limit=1` returns deals
- `GET /api/v1/categories` returns category tree
- `GET /admin/login` page renders

If 2 consecutive checks fail from any geo: SEV-2 alert.

A scripted full E2E synthetic runs every 10 minutes against staging:
- Login → fetch home → view a deal → add to cart → simulate checkout (test mode) → coupon issued → simulate redemption.

## Status page

`status.volu.ae` shows live system status:

- API
- Mobile apps
- Payment processing
- Search
- Notifications

Subscribers (merchant ops, internal team) get email/SMS on incident updates. Updated by IC during SEV-1/2 every 30 min.

## Capacity dashboards

Track utilisation trends to forecast scaling needs:

- App CPU/memory across all tasks
- DB CPU + storage growth
- Redis memory growth
- Queue throughput
- Daily GMV projecting forward

Reviewed monthly to plan upgrades.

---

## Observability hygiene rules

- **Every new service** must instrument: HTTP server, DB, external calls, custom counters for its key business events.
- **Every alert** must link to a runbook.
- **Every dashboard** must have an owner.
- **Logs are not the place to store data** — use the DB. Logs are for debugging.
- **High-cardinality labels are forbidden** in metrics (no user IDs in labels).
